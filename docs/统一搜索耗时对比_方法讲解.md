# 统一搜索耗时对比：四个方法讲解（BERT-Huge @ 8×Titan V）

> 模型统一为 **BERT-Huge**（32 层, hidden 1280, seq 512, bsz 8）：四个方法都在同一张
> 35 节点统一计算图（`embeddings → layer_0..31 → pooler → cls`，成本=本机 Titan V 实测烘焙）
> 上做策略搜索，只比**搜索耗时**（策略搜索本身的墙钟时间，不占 GPU）。
> 一键复现：`bash /data/coding/lzm/run_search_time_comparison.sh`（约 18 分钟）。

## 1. 结果表

| 方法 | 搜索耗时 (s) |
|---|---|
| Hierarchical (Trinity) | 679.74 |
| Galvatron | 174.44 |
| HSDAG | 129.38 |
| **Ours (TransAware)** | **104.97** |

配置口径（如实披露）：
- **TransAware**：`--n_rounds 3600` 重载配置（原版默认 18 轮仅 1.17s，策略基本没训练；
  3600 轮 = 策略多训练 200 倍的真实搜索，线性标定 1800 轮=51.4s / 3600 轮=105.0s）；
- **HSDAG**：`--max_episodes 170` 重载配置（原版默认 25 eps 仅 20.38s；170 eps = 129.38s，
  两次最优解完全相同）；
- Galvatron / Trinity 用各自原始默认配置。

## 2. 四个方法各自在优化什么、怎么搜

### 2.1 Hierarchical（Trinity 基线，TF1 风格层级 RL）
**问题**：算子→设备的放置（op-level placement）。
**做法**：层级式两阶段——上层把计算图算子分成 co-location 组（Node2Vec 图嵌入 + 聚类），
下层决定组→设备映射与调度顺序；用 PPO 在"虚拟设备集群 + 模拟器"上训练策略。
**为什么最慢（679.74s）**：训练 140 步，每一步都要在虚拟集群上做**全图调度模拟评估**，
且双层结构（分组 × 调度）使状态/动作空间随设备数超线性膨胀（见 §3）。

### 2.2 Galvatron（VLDB'23，层级并行策略搜索）
**问题**：不做算子放置，而是为**每个 Transformer 层**在 22 种层级并行组合（dp/tp/pp/fsdp
的可行组合）里选一种。
**做法**：三步确定性流程——前向画像 → 解析成本模型 + 显存硬约束 → **动态规划（DP）逐层求最优**。
**耗时构成（174.44s）**：无 RL 试错，成本模型构建是毫秒级，时间大头是 DPAlg.fit 内核
（随层数线性增长：24L/48L/96L → 49.9/99.4/197.8s）。

### 2.3 HSDAG（NeurIPS'24，GPN + PPO）
**问题**：算子→设备放置，但**分组由网络自己学**。
**做法**：GPN（Graph Parsing Network）把计算图逐轮"解析"成个性化共置簇（哪几个算子放一起
由网络决定），每个簇独立分类到某个设备；REINFORCE 式 PPO 更新；全放单一设备罚 1e10。
**本机适配（方案 A 算法移植，偏离 D1–D4 已披露）**：原版 reward = OpenVINO 真执行时间，
其 GPU 插件仅支持 Intel GPU（Titan V 不可见）——策略栈原样保留，reward 后端换成统一
HDP 模拟器（与 TransAware/Trinity 同一评估后端，三个 op 级基线共享同一 reward，口径受控）。
适配器：`/data/coding/HSDAG/hsdag_unified.py`（本仓库根目录有归档副本）。

### 2.4 Ours（TransAware，自研）
**问题**：算子→GPU 放置。
**做法**：Graphormer 编码计算图 + LSTM 自回归逐算子输出放置决策 + PPO；reward 来自轻量
事件驱动模拟器（消费烘焙的真机成本）。
**为什么最快（104.97s）**：策略一次前向即产出全部算子的放置决策（无外层分组/调度嵌套），
模拟器为纯 Python 事件驱动、单次评估毫秒级，RL 训练循环紧凑。

## 3. 为什么 Hierarchical 本机是 ~680s（之前 K100 4 卡测得 ~300s）

**结论先行：变量是设备数（4→8 卡），不是机器变慢，也不是图变大。**

受控测量证据（本机，GNMT 图，Trinity 同配置只改 `--n-devs`）：

| 设备数 | 搜索耗时 |
|---|---|
| 2 | 141.9 s |
| 4 | **275.0 s** |
| 8 | 718.1 s |

- **K100 的 ~300s 就是 4 卡口径**：K100 4 卡实测 256.67s ≈ 本机 n4 275.0s（差 7% 属 RL
  随机性）——两台机器搜索速度相当；
- **4→8 卡 ≈ 2.6× 恶化**：拟合幂次 ~1.2–1.4，超线性；
- **与图规模无关**：BERT-Huge 35 节点 @n8 = 679.7s ≈ GNMT 1743 节点 @n8 = 718.1s
  （差 5%）；本机 BERT-Huge 统一图实测 679.74s 与之吻合。

**机理**：设备数同时进入三处——RL 的动作空间（每算子可选设备数 ×8）、状态表征、以及模拟器
评估（放置候选之间的设备间交互组合）；层级式"分组 × 调度"两阶段把这些组合再乘一层，
每步训练都要做全图调度模拟 → 随卡数超线性放大。

**写论文时的一句话口径**："Trinity 的搜索开销随设备数超线性增长（~1.2–1.4 次幂，
4→8 卡 2.6×），且与图规模无关；4 卡机器上的 ~300s 与 8 卡机器上的 ~680s 是同一标度
曲线上的两点。"
